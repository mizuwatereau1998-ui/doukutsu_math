# トゲと2000m以降の操作密度の検証

## 前回が簡単だった理由

前回の波は固定の1.8〜2.2秒間隔だった。移動内容に応じて短くならず、同時封鎖は地上にいるときの判定だけだったため、上段でジャンプを繰り返せば避けられる構成が残っていた。最初に見つかった経路を採用し、少ない入力の抜け道や「段を変えずに跳ぶだけ」の経路を測っていなかった。単独障害物へ弱めるフォールバックが原因という証拠はなく、前回の生成数が増えてもこの配置上の余裕が残っていたことが主因。

今回は変更前のローカルスナップショットと現在の生成処理を、同じ低入力優先の経路探索で比較した。探索は0.05秒刻み、最大320状態、入力間隔0.18秒以上。最初に見つかった経路より入力が少ない経路を優先して残す。同じ段だけで抜けられるかは、上・中・下それぞれから段変更を禁止した別探索で検査した。上段ではその場ジャンプを許可している。

各距離帯60配置、計240配置。固定シードで900〜1490m、1500〜1992m、2000〜2983m、3000〜4967mに生成開始距離を分散。初期段・ジャンプ中・下降中を変え、実際の物理と衝突判定で入力列を再生した。

## 変更前後の比較

操作密度は探索開始から最後の障害物通過まで（接近の待ち時間を含む）の入力数÷秒数。「忙しい2秒」は各経路で最も入力が多い2秒間の回数を配置間で平均した値であり、走行中ずっとこの頻度になるという意味ではない。「同段通過」は3段のいずれかにとどまって全体を通過できた配置数。

| 生成距離帯 | 入力/秒 変更前→後 | 忙しい2秒の入力 前→後 | 波の到達間隔 前→後 | 同段通過 前→後 |
| --- | ---: | ---: | ---: | ---: |
| 900〜1500m | 0.462 → 0.543 | 1.18 → 1.80 | 2.045 → 1.052秒 | 49/60 → 60/60 |
| 1500〜2000m | 0.509 → 0.676 | 1.77 → 2.40 | 1.966 → 0.893秒 | 38/60 → 60/60 |
| 2000〜3000m | 0.532 → 1.047 | 2.20 → 3.87 | 1.819 → 0.812秒 | 31/60 → 0/60 |
| 3000m以降 | 0.526 → 1.333 | 2.25 → 4.65 | 1.790 → 0.584秒 | 31/60 → 0/60 |

2000m以降では操作密度が約2.0倍、3000m以降では約2.5倍。3000m以降は着地前に安全な段へ到達する時間も使って、さらに詰めている。2段上昇は中間段の着地と2回目の入力を待ち、1段下降などとは別の間隔にしている。

900〜2000mでは上段の同じ段でジャンプする抜け道を適応区間として残している。2000m以降は高い位置のコウモリと地上のトゲ等を組み合わせ、その抜け道を封じた。高いコウモリも従来の描画を使い、本体幅に応じて横方向へ拡大するので、不可視の横幅で封鎖していない。

## 現在の種類と生成状況

「同時封鎖」は波ごとに実際の衝突関数で2段が同時にふさがる瞬間があることを確認した数。安全段の切り替え数は、その確認済みの波の安全段の列の変化数。穴・トゲはジャンプで回避できるため地上での安全段を指し、これとは別に入力列全体の接触もチェックしている。

| 距離帯の開始 | 採用 | 障害物の波 | 安全段切替/配置（平均） | 入力数/配置（平均） | クモ＋コウモリ＋トゲ | 不採用候補（安全性／低入力） | 生成失敗 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 900m | 60/60 | 120 | 1 | 1.80 | 17/60 | 0／0 | 0 |
| 1500m | 60/60 | 180 | 2 | 2.72 | 47/60 | 0／0 | 0 |
| 2000m | 60/60 | 240 | 3 | 4.93 | 58/60 | 0／8 | 0 |
| 3000m | 60/60 | 300 | 4 | 6.12 | 60/60 | 0／8 | 0 |

240配置すべてで全波の2段同時封鎖、残る段の地上安全性、全経路の無衝突を検査した。2000m以降の120配置では、無操作・1入力だけ・同じ段にとどまる探索のいずれでも通過経路が見つからなかった。2000m以降は4入力未満、3000m以降は5入力未満で抜けられる候補を不採用にし、同じ波数・空中封鎖を持つ別経路で再試行する。低入力による不採用が発生しており、簡単な配置を積極的に除外できている。

種類名別の件数（各距離帯60配置、先頭2〜5波を使用）：

| 距離帯の開始 | 安全段の列の種類別件数 |
| --- | --- |
| 900m | `three-switch-01210`: 24、`three-switch-02120`: 11、`three-switch-10210`: 12、`three-switch-21021`: 13 |
| 1500m | `three-switch-01210`: 24、`three-switch-02120`: 11、`three-switch-10210`: 12、`three-switch-21021`: 13 |

## 連続走行と既存仕様

各開始距離から4シード×90秒、計16走行・24分相当をGame.updateで実行。算数中の回答操作を除外してアクション操作を数えた。生成、既存障害物との組み合わせ、クモの降下、コウモリの相対速度、接近時の加速も含む。開始した距離帯を超えて走るため、この表は開始点ごとの長時間試験であり、距離帯内だけの密度ではない。

| 開始距離 | 配置数（4走行） | アクション入力数 | 最短入力間隔 | アクション中に接近中の障害物が画面にない最長時間 | 不採用候補（安全性／低入力） | 生成失敗 |
| --- | --- | --- | ---: | ---: | ---: | ---: |
| 900m | 12 / 12 / 12 / 12 | 36 / 36 / 35 / 40 | 0.30秒 | 1.90秒 | 0／1 | 0 |
| 1500m | 11 / 11 / 11 / 11 | 54 / 51 / 52 / 58 | 0.25秒 | 0.88秒 | 0／2 | 0 |
| 2000m | 11 / 11 / 11 / 11 | 60 / 61 / 62 / 66 | 0.25秒 | 0.66秒 | 0／3 | 0 |
| 3000m | 12 / 12 / 12 / 12 | 72 / 72 / 72 / 71 | 0.25秒 | 0.72秒 | 0／2 | 0 |

全走行でミス0。これは経路が実際のゲーム更新で再生できたことの根拠であり、体感難易度の根拠には用いていない。難易度の根拠は上記の入力密度・同段通過・短い操作区間・安全段切り替えの比較である。

算数は従来通り150mの節目と安全区間を基準に出題し、初回6秒・最短2秒、問題中の通常障害物なし。5ミス終了・通常問題と回復問題・常設3段・クモの糸と脚に判定なし・ポップンと追手のアニメーションは維持した。高難度の連続波は途中で消さず通過を待つため、出題が節目より遅れる従来の仕様も維持する。

## トゲ・開発モード・ブラウザ

自動テスト66件が成功。トゲの三角形と本体の円の接触、三角形の空白部分、先端より上、ジャンプでの通過、下降中の接触、無敵、上中段に穴が生成されないことを検査した。不可避な全段封鎖を不採用にするテストも維持している。

HTTP経由のChromiumでPC操作、スマホの上下スワイプ、縦向き自動停止、4波の生成と描画、上下段のトゲ描画、開発用4距離の開始・再挑戦・通常モード復帰・ゲームオーバー時のlocalStorage非更新を確認した。追加の `tests/browser_pressure.py` では、3000mから通常のrequestAnimationFrameを動かし、上下キーイベントを入力して24秒間走行した。22入力・算数2問・ミス0・JavaScript例外0。Game.updateをテストから手動実行する方式ではなく、ブラウザ本来の進行と入力処理を通した。file://は管理ポリシーでスキップ。実機スマホと人の主観的なプレイ評価は未実施。

開発開始はURLの `?devStart=2000` またはコンソールの `PopEscape.startTest(2000)`。対応距離は900・1500・2000・3000m。通常モード復帰は `PopEscape.endTest()`。テスト走行では最高記録を保存しない。

## 再実行と検証の範囲

```sh
npm run check
npm test
node tests/difficulty.mjs
# HTTPサーバーを起動した別ターミナルで
python3 tests/browser_smoke.py
python3 tests/browser_pressure.py
```

生データは [difficulty-before.json](difficulty-before.json) と [difficulty-after.json](difficulty-after.json)。変更前の比較は今回の編集前に保存したローカルスナップショットを使用した。任意の比較用スナップショットを用意する場合は `node tests/difficulty.mjs --source /path/to/snapshot`（配下にjs/config.js等が必要）で共通の低入力優先探索を使って集計できる。

探索は量子化・状態数上限・時間刻みを持つため、数学的な完全最短経路の証明や、全ての人間の操作時刻の網羅ではない。保持する実際の座標は丸めず、採用経路は1/120秒の物理で衝突しないことを確認する。低入力経路の見逃しや、存在する経路を見つけられず不採用にする可能性は残る。0.05秒刻みへの改善では、密な配置の途中から再探索する場合の取りこぼしも減らした。

この検証で2000m以降の無操作・1入力・同段探索が0件だったことは有限サンプルでの観測結果。上級者の体感については開発モードで実際に確認し、必要ならconfig.jsの余裕時間・波数・入力数下限から調整する。
